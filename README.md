# Mapline

Небольшой сервис для подключения карточки организации на Яндекс.Картах и просмотра ее рейтинга и отзывов.

Проект сделан как тестовое приложение на Laravel и Vue 3:

- авторизация одного пользователя через Laravel Sanctum;
- сохранение ссылки на карточку организации;
- загрузка рейтинга, количества оценок и количества отзывов;
- сбор доступных отзывов с постраничной загрузкой по 50 записей;
- фоновая синхронизация через Laravel Queue;
- сохранение истории запусков и снимков данных организации.

## Как запустить локально

### Требования

- PHP 8.3 или новее;
- Composer;
- Node.js 20 или новее;
- MySQL 8;
- запущенный worker очереди.

### Установка

```bash
composer install
copy .env.example .env
php artisan key:generate
```

Создайте базу MySQL и укажите ее реквизиты в `.env`:

```dotenv
DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=mapline
DB_USERNAME=root
DB_PASSWORD=
```

После этого выполните миграции и сидер:

```bash
php artisan migrate --seed
npm install
npm run build
```

Для разработки с автоматической пересборкой фронтенда можно использовать:

```bash
npm run dev
```

В отдельном окне запустите обработчик фоновых задач:

```bash
php artisan queue:work --tries=3
```

Laravel-приложение можно открыть через OpenServer или встроенный сервер:

```bash
php artisan serve
```

После выполнения сидинга доступен пользователь:

```text
Email: admin@mail.ru
Пароль: 12345678
```

Пароль предназначен только для локального демонстрационного пользователя. Для реального окружения его нужно заменить.

## Переменные окружения

```dotenv
YANDEX_MAX_REVIEWS=600
YANDEX_REQUEST_DELAY_MS=350
```

`YANDEX_MAX_REVIEWS` ограничивает количество загружаемых отзывов за один запуск. `YANDEX_REQUEST_DELAY_MS` задает минимальную паузу между запросами страниц отзывов.

## API

Публичная часть приложения отдается маршрутом из `routes/web.php`, а данные загружаются через API:

```text
POST /api/login
GET  /api/me
POST /api/logout

GET  /api/organization
POST /api/organization
GET  /api/organization/reviews?page=1
GET  /api/organization/status
```

Маршруты организации защищены `auth:sanctum`. Сессия работает через cookie, а перед авторизацией фронтенд получает CSRF-cookie через `/sanctum/csrf-cookie`.

## Как работает синхронизация

1. Пользователь вставляет ссылку на карточку.
2. `OrganizationController` валидирует запрос и нормализует URL.
3. Организация и запись запуска сохраняются в базе со статусом `queued`.
4. В очередь отправляется `SyncOrganizationJob`.
5. Worker запускает `OrganizationSyncService`.
6. Сервис вызывает `YandexMapsParser`.
7. Парсер получает страницы отзывов, извлекает данные и передает прогресс в сервис.
8. Сервис обновляет организацию, отзывы, запуск синхронизации и снимок.
9. Vue периодически запрашивает `/api/organization/status`.
10. После завершения загружается актуальная страница отзывов.

Парсинг не выполняется внутри HTTP-запроса сохранения ссылки. Это важно для карточек с большим количеством отзывов и для подключения нескольких филиалов.

## Подход к парсингу

В текущей версии используется HTTP-запрос к страницам Яндекс.Карт с разбором JSON, который присутствует в HTML страницы, и резервным разбором отдельных HTML-метаданных.

### Почему выбран этот вариант

Плюсы:

- не требуется запускать браузер на сервере;
- ниже потребление памяти и CPU;
- проще масштабировать очередь;
- можно ограничивать частоту запросов;
- результат удобно тестировать на сохраненных HTML-примерах.

Минусы:

- структура встроенного JSON может измениться;
- часть данных может появляться только после выполнения JavaScript;
- защита Яндекса может вернуть страницу проверки вместо карточки;
- без официального API нельзя гарантировать постоянную стабильность источника.

Headless-браузер был бы устойчивее к страницам, которые полностью строятся JavaScript-кодом, но он тяжелее для shared hosting: нужны Chromium-зависимости, больше памяти и отдельное управление сессиями. Для небольшого прототипа HTTP-подход проще и дешевле в эксплуатации.

## Устойчивость к изменению разметки

Парсер не считает любой HTML успешным ответом.

Он:

- проверяет HTTP-коды `403` и `429`;
- обнаруживает признаки SmartCaptcha и страницы проверки браузера;
- проверяет, что в ответе найдены данные организации или отзывы;
- сравнивает заявленное количество отзывов с результатом разбора;
- выбрасывает `YandexSourceChangedException`, если карточка сообщает о наличии отзывов, но парсер получил пустой результат;
- сохраняет ошибку в `sync_runs.error` и `organizations.last_error`;
- пишет подробности исключения в Laravel log.

Благодаря этому изменение формата страницы не приводит к незаметной замене ранее сохраненных отзывов пустым набором.

## Очередь и масштабирование

Задача `SyncOrganizationJob`:

- выполняется в фоне;
- имеет ограничение `timeout = 240`;
- делает до трех попыток;
- использует backoff `10`, `30` и `120` секунд;
- сохраняет статус и прогресс в базе.

При сети из нескольких десятков филиалов задачи должны обрабатываться несколькими worker-процессами. Для production-сценария очередь лучше вынести на Redis или отдельный managed queue, а worker запустить под Supervisor или другим менеджером процессов.

Сейчас для простого развёртывания используется database queue:

```dotenv
QUEUE_CONNECTION=database
```

## Защита от блокировок

В текущей реализации предусмотрены:

- пауза между запросами страниц;
- повторы временных HTTP-ошибок;
- ограничение общего количества отзывов;
- тайм-ауты соединения и ответа;
- распознавание `403`, `429` и страниц проверки;
- остановка синхронизации при обнаружении блокировки.

Для регулярной загрузки большого количества карточек в production стоит добавить:

- общий rate limiter на источник;
- случайную небольшую задержку вместо фиксированной;
- экспоненциальный backoff для временных ошибок;
- ограниченный пул прокси, если это разрешено правилами площадки;
- ротацию обычных браузерных User-Agent;
- circuit breaker, чтобы временный бан не создавал лавину новых запросов;
- отдельный статус `blocked` и уведомление оператора.

Прокси и User-Agent нельзя ротировать бесконтрольно: слишком частая смена параметров сама может выглядеть подозрительно. Лимиты должны настраиваться централизованно для всего пула филиалов.

## Идемпотентность и история

Дубли отзывов не создаются благодаря уникальному индексу:

```text
organization_id + external_id
```

При повторной синхронизации:

- существующий отзыв обновляется через `updateOrCreate`;
- новый отзыв добавляется;
- отзывы, которых больше нет в текущем ответе источника, помечаются `is_current = false`;
- предыдущие записи физически не удаляются.

Для истории используются две таблицы:

- `sync_runs` — история запусков, статусы, прогресс и ошибки;
- `organization_snapshots` — состояние рейтинга, счетчиков и краткая информация о составе отзывов на момент запуска.

Поле `content_hash` помогает определить изменение текста или основных атрибутов отзыва.

## Обработка ошибок

Ошибки разделены на несколько типов:

- ошибка валидации ссылки;
- недоступный источник;
- ответ с защитой от автоматических запросов;
- изменение структуры страницы;
- пустой или неполный ответ;
- ошибка фоновой задачи.

Пользователь видит ошибку в интерфейсе. При этом технические подробности сохраняются в `storage/logs/laravel.log`, а состояние последнего запуска доступно через API.

## Развёртывание на Timeweb

Для shared hosting нужен PHP-сайт, MySQL-база и возможность запускать очередь.

### Файлы

Загрузите содержимое проекта на сайт, но не переносите:

```text
.env
vendor/
node_modules/
public/build/
```

На сервере выполните:

```bash
composer install --no-dev --optimize-autoloader
npm ci
npm run build
php artisan migrate --force
php artisan db:seed --force
php artisan config:cache
php artisan route:cache
```

Корень сайта должен указывать на папку `public`.

### Настройки production

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_URL=https://example.com

DB_CONNECTION=mysql
DB_HOST=...
DB_PORT=3306
DB_DATABASE=...
DB_USERNAME=...
DB_PASSWORD=...

QUEUE_CONNECTION=database
```

После изменения `.env`:

```bash
php artisan config:clear
php artisan config:cache
```

Обработчик очереди должен работать постоянно. Если на тарифе нет SSH или фоновых процессов, можно использовать cron:

```text
* * * * * php /path/to/project/artisan queue:work --stop-when-empty --tries=3
```

Для стабильной работы лучше использовать отдельный worker-процесс. Без worker синхронизация будет оставаться в статусе `queued`.

## Что стоит доделать для production

- вынести очередь из MySQL в Redis;
- добавить отдельную страницу истории синхронизаций;
- хранить полные diff-снимки отзывов;
- добавить ограничение частоты запусков на пользователя и организацию;
- добавить мониторинг очереди и уведомления о блокировке источника;
- покрыть парсер набором HTML/JSON fixtures для разных вариантов страницы;
- добавить Supervisor-конфигурацию для worker;
- добавить CI с запуском тестов и production-сборки;
- использовать отдельные секреты и не хранить демонстрационный пароль в исходниках production-окружения.
